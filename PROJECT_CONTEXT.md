# 🦈 Employee Time Tracker — проектный паспорт

Обновлено: 2026-11-19. Назначение: сохранить контекст разработки, решения и дальнейший план.

## Цель
Веб-приложение для офисной компании: фиксация рабочих статусов сотрудников, графики, план/факт, управленческая аналитика. Приоритет — удобство руководителя, единые правила компании, проверяемые данные. Не делать автоматических выводов о дисциплинарных нарушениях или физическом отсутствии по одному лишь отсутствию записи.

## Инфраструктура
- GitHub: https://github.com/bgshark-cmd/employee-time-tracker-demo
- GitHub Pages: https://bgshark-cmd.github.io/employee-time-tracker-demo/
- Supabase project ref: cxqxsnkgytwzowoizjrk
- Авторизация Supabase Auth, клиент supabase-js 2, HTML/JS на GitHub Pages.
- Владелец записей определяется через owner_id и RLS. Не публиковать пароли, service_role и другие секреты.
- Данные в Supabase, а не в HTML. Планируется возможный перенос на собственный сервер.

## База
- database/001_initial_schema.sql: ett_employees, ett_intervals, ett_preferences, RLS.
- database/002_timer_transitions.sql: RPC ett_switch_interval, ett_stop_interval.
- database/003_employee_schedules.sql: ett_schedules, индивидуальные недельные расписания.
- database/004_company_schedule.sql: ett_company_schedule, общий график компании.
- Пользователь подтвердил выполнение миграции 003. Версия v1.1 работала, что указывает на работоспособность общего графика после 004.
- Существующие индивидуальные графики сохраняются как исключения; общий применяется при отсутствии исключения.
- Текущие ограничения: смены в пределах одних суток; часовой пояс устройства должен совпадать с сохранённым для точного план/факт; лимит 1000 интервалов в некоторых отчётах; текущий незавершённый день исключается из итогового план/факт.

## UX и управленческая логика
- Главный экран — рабочий пульт: сразу видно сотрудников и можно менять их активность без перехода в Команду.
- Раздел Команда — управление сотрудниками и карточками.
- Раздел Настройки — общий график; в карточке — необязательное индивидуальное исключение.
- Сигналы превышения лимитов означают «требует проверки», а не доказательство нарушения.
- Нет активного таймера ≠ сотрудник отсутствует. Зарегистрированное время ≠ продуктивность.

## Состояние пилота
Пользователь подтвердил работу v1.2 и хочет накопить данные до улучшения аналитики. Пилот пока для руководителя под собственным аккаунтом, а не для самостоятельного доступа сотрудников. Не делиться руководительскими учётными данными с командой.

## Следующие этапы (не реализованы)
1. Пилот 2–3 недели с тестовыми/реальными данными после проверки правомерности и информирования сотрудников.
2. Контроль качества данных: забытые таймеры, аномально длинные интервалы, пропущенные переключения, исправление ошибок и аудит.
3. Разработка KPI на основе накопленных данных: план/факт, динамика, повторяющиеся отклонения, отчёты.
4. v1.3 Team Access: отдельные учётные записи, роли руководителя и сотрудника, связь auth user с employee record, доступ сотрудника только к своим данным, расширенная RLS, приглашения.
5. Перенос порогов перерывов из localStorage в Supabase.
6. Пагинация вместо лимита 1000, резервные копии, безопасность, тестирование нескольких аккаунтов.

## Рабочие принципы
- Менять версии инкрементально: новый HTML для новых фич, предыдущую проверенную версию не ломать.
- Писать изменения напрямую в GitHub и давать тестовую ссылку; пользователю не нужно вручную копировать код.
- Для новых таблиц отдельные SQL-миграции; не запрашивать секреты.
- Объяснять шаги простым русским языком, тестировать по одному этапу.
